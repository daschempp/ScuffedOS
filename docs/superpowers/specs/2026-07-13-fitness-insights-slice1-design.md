# Insights — WHOOP-style derived coaching, fitness slice 1

**Date:** 2026-07-13 · **Status:** approved design (brainstormed with user)
**Branch:** `fitness-insights-slice1` off `main` (unrelated to the in-flight `m10-messaging-slice1`).
**One-line:** a new **Insights** tab that turns the fitness data we already sync into short,
warm coaching narratives — the way WHOOP's app does, but generated by us because the WHOOP API
exposes only raw numbers (see §2).

---

## 1. Goal

Give the user a WHOOP-app-style read on their body each day — "recovery's green, you're primed
for a hard session" / "third short-sleep night, ease off" — as a browsable feed, generated from
the recovery/sleep/strain/HRV data already landing in `daily_snapshots`. Fitness-only for this
slice, but the engine is built so email/finance/school insights plug into the same table, phraser,
and feed later (§8) — i.e. this is the first concrete slice of the "proactive layer / Recovery
Governor / Morning Pulse" sketched in the 2026-07-11 audit, not a competing structure.

## 2. Why we generate this ourselves

A deep-research pass (21 claims, 3-vote adversarial verification) confirmed: the **public WHOOP
API (v1/v2) returns only numeric/boolean/enum fields** — `recovery_score`, `resting_heart_rate`,
`hrv_rmssd_milli`, `spo2_percentage`, `skin_temp_celsius`, sleep-stage durations, `strain` (0–21),
workout metrics — across a narrow 13-endpoint read-only surface. It exposes **no narrative,
journal, insight, or coaching text**. WHOOP's own "WHOOP Coach" narrative is an in-app GPT-4
feature with no API endpoint; WHOOP's developer community has an open, unanswered request to
"make journal data available in the API." So the insight layer is ours to build — model the WHOOP
data as numeric time-series only, and generate any prose client-side. This design does exactly
that.

## 3. User-approved forks

1. **Scope: fitness-first, engine domain-extensible.** Ship WHOOP-parity fitness coaching now;
   build the table/rules/phraser/feed so other domains join later without a schema change.
2. **Generation: hybrid — rules pick, Claude phrases.** Deterministic rules detect what is
   noteworthy and hand Claude *only the verified facts*; Claude phrases them. Claude never sees
   raw data it could hallucinate a number from.
3. **Freshness: cached.** Insights are computed and stored, not regenerated per view. Concretely:
   **generate once per day** (§6c), reads are pure cache, manual refresh available.

## 5. Architecture — three clean layers

```
daily_snapshots / workouts ──► RULES ──► [Signal] ──► PHRASER ──► insights rows ──► GET /api/insights ──► Insights tab
     (existing data)         (pure fns)  (facts)   (Claude 1-shot)  (new table 0010)   (pure cache read)     (new screen)
```

Each layer is independently testable and has one job. Data flows one way; the read path never
touches the rules or the LLM.

### 5a. Rules — `app/insights/rules.py` (pure, deterministic, no LLM)

Each rule is a pure function `(context) -> Signal | None` over the snapshot history for a day plus
a trailing baseline window (default 7 prior days, computed from `daily_snapshots`). A `Signal` is:

```
Signal(
  code:  str,          # stable id, e.g. "recovery_primed" — also the dedup key
  tone:  str,          # "positive" | "neutral" | "caution"
  facts: dict,         # the exact numbers the rule saw: {"recovery_pct": 72, "baseline": 58, ...}
  template: str,       # deterministic fallback wording (§6d), interpolated from facts
)
```

Slice-1 fitness rules (each emits a Signal or nothing; the recovery-band rule always emits, as the
anchor card):

| code | fires when | tone |
|---|---|---|
| `recovery_band` | anchor — emits whenever `recovery_pct` is present (generation is gated on that, §6c, so in practice it always emits). WHOOP bands: `≥ 67` green / `34–66` yellow / `< 34` red | pos / neutral / caution |
| `recovery_trend` | today vs 7-day baseline differs by a material margin | pos if up, caution if down |
| `strain_recovery_balance` | high strain on low recovery (**overreaching**) OR high recovery with low strain so far (**primed & underused**) | caution / positive |
| `sleep_performance` | `sleep_quality_pct` low, or a ≥2-night short-sleep streak (`sleep_hours` below threshold) | caution |
| `hrv_trend` | `hrv_ms` materially below (or above) baseline | caution / positive |
| `rhr_elevation` | `resting_hr` materially above baseline (possible illness/fatigue) | caution |

Thresholds live as named constants at the top of the module (single source, easy to tune).
Rules operate only on fields that are present; a missing metric means the rule no-ops, never
guesses.

### 5b. Phraser — `app/insights/phraser.py` (the "Claude phrases it" step)

Input: the list of fired `Signal`s (codes + facts) for a day. It builds a tightly-constrained
prompt — the assistant's warm plain-text voice, **"use only these facts, invent no numbers,
1–2 sentences per insight"** — and calls `llm.complete()` (§6b) on the **chat tier**
(`settings.assistant_model`; single-domain phrasing doesn't need the heavy model). Output: a
`headline` (≤ ~120 chars) + `body` (prose) per card, associated back to each signal's `code`/`tone`.

The phraser is the *only* place the LLM touches this feature, and it receives *derived facts,
never raw snapshots* — this is what makes the hybrid hard to hallucinate.

### 5c. Generation orchestrator — `app/insights/engine.py`

`generate_for_day(day) -> int` runs the rules over the day's snapshot + baseline, calls the
phraser, and **upserts** one `insights` row per fired signal `code`. Returns the count. Idempotent
via the unique key (§6a), so re-running replaces rather than duplicates. If `llm.available()` is
false it still writes rows, worded from each signal's `template` (§6d), with `source="rules"`.

## 6. Backend detail

### 6a. Data model — migration `0010`, table `insights`

| column | type | note |
|---|---|---|
| `id` | int PK | |
| `owner` | str(64), index, default `me` | matches every other table's owner scoping |
| `day` | date, index | the calendar day the insight is about |
| `domain` | str(16), index | `"fitness"` this slice; the extensibility axis (§8) |
| `code` | str(40) | the signal code; part of the dedup key |
| `tone` | str(12) | `positive` \| `neutral` \| `caution` |
| `headline` | str(160) | short title |
| `body` | Text | the narrative prose |
| `signals_json` | JSON | the rule's `facts` — powers the UI metric chips + the rules fallback |
| `source` | str(8) | `"llm"` or `"rules"` — honesty/debug: was it phrased or templated |
| `created_at` / `updated_at` | tz datetime | |

**Unique:** `(owner, domain, day, code)` → regeneration upserts. Multiple codes/day = multiple
cards = a feed. Follows `DailySnapshot`'s owner-scoped, derive-friendly shape.

### 6b. `llm.complete()` — new one-shot on the existing seam

Add to `llm.py` alongside `stream()`:

```
def complete(*, model: str, system: str, messages: list) -> str
```

Real path: `messages.create(...)` and return the concatenated text. Fake path: delegate to the
installed fake exactly like `stream()` does (so `llm.configure(fake)` covers it in tests).
Disabled path (`_override is None`): raise `RuntimeError`, which the engine catches → rules
fallback. This is additive; the assistant loop's `stream()` is untouched.

### 6c. When generation runs (the "cached" fork, concretely)

- **Primary:** hook `generate_for_day(today)` into the fitness sync, right after
  `_sync_provider` upserts snapshots. The guard is two conditions, both required:
  (a) today's recovery is present (`recovery_pct` not null — WHOOP's `SCORED` state), so the anchor
  card always has a value; and (b) no `insights` row exists yet for `(owner, "fitness", today)`.
  Early ticks before recovery scores simply wait; the first tick after recovery lands generates;
  later same-day ticks find condition (b) false and skip. Recovery is the morning anchor and is
  stable once scored, so one generation per day captures the coaching call and later syncs don't
  re-spend tokens. **Net cost ≈ 1 LLM call/day.**
- **First connect:** the WHOOP `on_connected` hook already kicks a sync (whoop.py:170), so backfill
  + first-day generation happen naturally on connect.
- **Manual:** `POST /api/insights/refresh` forces `generate_for_day(today)` regardless of the
  once-a-day guard (the "refresh" affordance).
- **Reads never generate.** `GET /api/insights` is a pure cache read, preserving the fitness-domain
  invariant that reads never call a provider/LLM.

### 6d. Degradation

If the LLM is unavailable (no key, offline, disabled), the engine writes rows worded from each
signal's `template` string, `source="rules"`. The tab still renders real, if plainer, coaching.
No path leaves the tab empty when there is snapshot data.

### 6e. Endpoints — `app/routers/insights.py` (prefix `/api/insights`)

| method | path | returns |
|---|---|---|
| `GET` | `/api/insights?date=` | `InsightsDay`: `{ date, has_data, cards: [InsightCard] }` for the day (default today) — pure cache read via a new `store.list_insights(day)` |
| `POST` | `/api/insights/refresh` | force-regenerate today; returns the fresh `InsightsDay` |

`InsightCard` (pydantic, in `schemas.py`): `{ id, domain, tone, headline, body, signals, source }`.
Response-model + thin-router conventions mirror `routers/fitness.py`. Registered in `main.py`
next to the other routers.

### 6f. Store methods

- `list_insights(day, domain="fitness") -> list[dict]` — owner-scoped read, ordered by tone
  severity then id (anchor/positive first is a UI choice; finalized in impl).
- `upsert_insight(day, domain, code, tone, headline, body, signals, source) -> dict` — get-or-create
  by the unique key, mirroring `upsert_snapshot`'s pattern.

### 6g. Assistant tool

Add a `get_insights` read tool in `tools.py` (mirrors `_get_fitness_today`, tools.py:389) so chat
can reference the same cached read ("what's my read on today?") without recomputing. Read-only.

## 7. Frontend — `frontend/src/screens/InsightsScreen.jsx`

- A **feed of insight cards**. Each card: a tone-colored accent (green/honey/clay via existing
  design tokens), a display-font `headline`, the `body` prose, and a row of **metric chips** built
  from `signals_json` (e.g. "Recovery 42% · HRV 31 ms ↓ · RHR +4"). Reuses `Card`, `Badge`, and the
  existing `.kit-insight` styling.
- **Header:** title + a Refresh `IconButton` (`refresh-cw`) calling `POST /api/insights/refresh`
  then refetching.
- **States:** not-connected → `NotConnectedCard` (deep-links to Settings › Connectors);
  needs-reauth → `NeedsReauthBanner`; connected-but-no-cards-yet → a calm "No read yet — it'll
  appear after your next sync." Mirrors `FitnessScreen`'s status handling (FitnessScreen.jsx:92).
- **Registration:** import + `else if (screen === 'insights')` in `App.jsx:140`; a
  `{ id: 'insights', label: 'Insights', icon: 'sparkles' }` item in the **Health** section of
  `shell/Sidebar.jsx:14` (directly under Fitness). Migrates to an "Intelligence" grouping when it
  goes cross-domain.
- **De-dupe:** replace the hardcoded insight line at `FitnessScreen.jsx:200` with the top cached
  card (or a link to the Insights tab) so there's one source of truth.
- **Transport:** add `insights(date)` and `insightsRefresh()` to `lib/api.js` beside the `fitness*`
  helpers.

## 8. Designed-for-more (not built this slice)

Because cards carry a `domain` and a generic `signals_json`, a later finance/school/email insight
is just a new `rules_<domain>.py` emitting `Signal`s into the **same** engine → phraser → table →
feed — no schema change, no new endpoint. A future Home "Morning Pulse" widget is this same
`GET /api/insights` filtered to today across domains. This is the deliberate first slice of the
2026-07-11 audit's proactive layer; nothing here forecloses it.

## 9. Testing

- **Rules** (`test_insights_rules.py`) — pure unit tests with synthetic snapshot fixtures: green /
  yellow / red recovery, overreaching (high strain + low recovery), primed-underused, short-sleep
  streak, HRV dip, RHR elevation, and missing-metric no-ops. No LLM, no DB.
- **Phraser / engine** (`test_insights_engine.py`) — `llm.configure(fake)` asserting the phraser is
  handed the right facts and no raw snapshot; assert the `template` fallback fires and rows land
  with `source="rules"` when the LLM is disabled; assert the once-a-day guard.
- **Endpoint + store** (`test_insights_api.py`) — seed snapshots, assert `GET` returns cached cards
  and never triggers generation; assert `POST /refresh` regenerates. Follows the repo's
  `fakes.py`/`configure()` conventions.
- Full suite stays green; report the pass count on completion.

## 10. Slice boundary

**In:** `insights` table (`0010`) · `app/insights/{rules,phraser,engine}.py` · `llm.complete()` ·
once-a-day post-sync generation + `/refresh` · `GET /api/insights` · store read/upsert ·
`get_insights` assistant tool · `InsightsScreen` + nav registration + `FitnessScreen` de-dupe ·
tests. Fitness domain only.

**Out (future slices):** finance/school/email rule modules · a cross-domain Home "Morning Pulse"
widget · any live/intraday regeneration beyond once-a-day + manual refresh · per-insight
user feedback/dismissal · trend charts inside the tab.

## 11. Open questions (non-blocking; decide in impl)

- Whether `get_insights` should also expose the week (defer unless the assistant needs it).
